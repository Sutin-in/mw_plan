# คู่มือส่งมอบให้ฝ่าย IT — เชื่อม HOSxP และเปิดใช้ระบบจริง (Wave 10B-2)

ระบบควบคุมแผนและ PPR (Phase 1) สร้างและทดสอบครบแล้วกับข้อมูลจำลอง (MOCK) ส่วนที่เหลือคือการเชื่อมกับ
HOSxP ของโรงพยาบาลและเปิดใช้บน server จริง คู่มือนี้คือลำดับงานทั้งหมด ทำตามทีละขั้น
แล้วเก็บหลักฐานลง `docs/GO_LIVE_CHECKLIST.md`

> **หลักที่ต้องรักษา**
>
> - ระบบ **อ่าน HOSxP อย่างเดียว** ไม่เขียน ไม่แก้ HOSxP ทุกกรณี
> - ระบบ **ไม่เดา** ชื่อตาราง คอลัมน์ หรือค่าสถานะของ HOSxP สิ่งเหล่านี้ IT เป็นผู้เขียนในไฟล์ query ของโรงพยาบาล
> - ห้ามเก็บรหัสผ่าน certificate หรือ private key ไว้ใน repository ค่าลับอยู่ใน `.env` บน server เท่านั้น
> - ห้ามคัดลอกข้อมูล HOSxP / ข้อมูลผู้ป่วยมาไว้ในฐานข้อมูลทดสอบ
> - ยอดเบิก/คืนจากคลังเป็นข้อมูลของ HOSxP แสดงในรายงานเท่านั้น **ไม่ลงบัญชีแผน** (D-39)

## ขั้นที่ 1 — เตรียม server และฐานข้อมูลระบบ

1. ติดตั้งตาม `DEPLOY_PRODUCTION.md` §1–§3: Python 3.12, Node.js, PostgreSQL 16, โค้ดตาม tag ที่ส่งมอบ
2. สร้างบัญชีฐานข้อมูล 2 บัญชี (เจ้าของ schema / บัญชีที่ระบบใช้ สิทธิ์น้อย) และฐานข้อมูลใหม่ที่ **สะอาด**
   (ห้ามใช้ฐานข้อมูลที่เคยเปิดโหมดทดลอง `--demo`)
3. เขียน `.env` บน server: `PPR_PROFILE=production`, บัญชีทั้งสอง, `PPR_SESSION_SECRET` (ยาวอย่างน้อย 32 ตัวอักษร),
   ค่า HTTPS ของหน้าเว็บ (`PPR_UI_SECURE_COOKIES=1`, `PPR_UI_TRUST_PROXY`, `PPR_UI_HOST`, `PPR_API_URL`), `PPR_BACKUP_DIR`
4. สร้าง schema:
   ```
   .venv\Scripts\python -m ppr.cli migrate
   ```

## ขั้นที่ 2 — เชื่อม HOSxP (อ่านอย่างเดียว)

ทำตาม `HOSXP_CONNECTION.md` ขั้นที่ 1–4 (หรือใช้ชุด interface views):

1. สร้างบัญชี HOSxP ที่ **อ่านได้อย่างเดียว** จำกัดให้เข้าได้จาก IP ของ server นี้เท่านั้น
2. ใส่ `PPR_HOSXP_MODE=sql`, `PPR_HOSXP_DATABASE_URL`, `PPR_HOSXP_QUERIES` ใน `.env`
   - ถ้าบัญชีผู้ใช้ HOSxP อยู่อีก server ใส่ `PPR_HOSXP_AUTH_DATABASE_URL` (อ่านอย่างเดียว) ด้วย (D-41)
   - ทดสอบการเชื่อมต่อ: `python -m ppr.cli hosxp-check --user <ชื่อผู้ใช้ทดสอบ>` (ไม่ถามและไม่แสดงรหัสผ่าน)
3. เขียน `hosxp_queries.toml` (ไฟล์ของโรงพยาบาล ไม่ commit) จากแบบ:
   - query ที่จำเป็น 8 รายการ: หัว PR, รายการใน PR, หน่วยงาน, สินค้า, แหล่งเงิน, หมวดงบ, ผู้ใช้ (login), ข้อมูลผู้ใช้
   - `[status_map]` ค่าสถานะ PR ของ HOSxP → สถานะมาตรฐาน **ใส่เฉพาะค่าที่มีหลักฐาน** ถ้ายังไม่รู้ ให้เว้นไว้ (ระบบถือว่า UNKNOWN ไม่เดา)
   - `[stock_movement]` (ไม่บังคับ) ยอดเบิก/คืนจากคลังกลาง พร้อมผู้ยืนยัน วันที่ เลขอ้างอิง และการจับคู่ประเภทเบิก/คืน
     ถ้ายังไม่พร้อม ให้เว้นไว้ รายงานจะแสดง "ยังไม่มีข้อมูล"
4. กติกาสำคัญของ query: รหัสหน่วยงาน/สินค้า/แหล่งเงิน/หมวดงบที่อ้างถึงกันต้องเป็น **รหัสชุดเดียวกัน**
   และจำนวนในยอดเบิก/คืนต้องเป็น **หน่วยเดียวกับสินค้าใน PR**

## ขั้นที่ 3 — ตรวจการเชื่อม HOSxP: `hosxp-verify`

```
.venv\Scripts\python -m ppr.cli hosxp-verify --pr <เลขที่ PR จริง> --out D:\ppr\golive\hosxp_verify.md
```

- คำสั่งนี้ **อ่านอย่างเดียว** ไม่เขียนข้อมูลใด ๆ และไม่พิมพ์ชื่อบุคคล รหัสผ่าน หรือข้อมูลผู้ป่วย
- ใส่ `--pr` ได้หลายครั้ง แนะนำ: PR ปกติ 1 ใบ (เช่น PR 6907912), PR ที่ถูกยกเลิกแล้ว 1 ใบ (ถ้ามี)
- ผลแต่ละบรรทัด:

| ผล | ความหมาย | ต้องทำ |
|---|---|---|
| PASS | ตรวจแล้วถูกต้อง | — |
| FAIL | ผิด ต้องแก้ก่อนเปิดใช้ (คำสั่งจบด้วย exit code 1) | แก้ query / สิทธิ์บัญชี แล้วรันใหม่ |
| OPEN | ยังไม่มีหลักฐาน / ยังไม่ได้ตัดสินใจ **ไม่ใช่ PASS** | ส่งหลักฐานตามตารางท้ายคู่มือ |
| INFO | ข้อมูลประกอบ | อ่าน |

- สิ่งที่ตรวจ: บัญชี HOSxP มีสิทธิ์เกินการอ่านหรือไม่ (อ่านจาก catalogue ของฐานข้อมูล ไม่ลองเขียน),
  master 4 ชุด (มีข้อมูล ไม่ซ้ำ หมวดแม่ครบ), PR ที่ระบุ (ปีงบ, รหัสตรงกับ master, ยอดรวม, ค่าสถานะ),
  การจับคู่สถานะยกเลิก (D-30, OPEN จนกว่าจะแนบหลักฐาน แม้ตั้งค่าแล้ว), G-4, รูปแบบ login (D-25), ยอดเบิก/คืน (D-39)
- การตรวจบัญชี HOSxP ใช้หลัก **อนุญาตเฉพาะสิทธิ์อ่าน** (SELECT / SHOW VIEW / USAGE) สิทธิ์อื่นใดที่พบ (รวมสิทธิ์ระดับคอลัมน์ view sequence และ role) เป็น FAIL
- ผลสรุปบรรทัดสุดท้าย: `PASS` เฉพาะเมื่อไม่มีอะไรค้าง ถ้ามี OPEN จะเขียนว่า `NO FAIL - n OPEN (not PASS)`

## ขั้นที่ 4 — ตรวจความพร้อมก่อนเปิดครั้งแรก: `first-start --check`

```
.venv\Scripts\python -m ppr.cli first-start --check --out D:\ppr\golive\first_start.md
```

- **อ่านอย่างเดียว** ไม่แก้อะไร ตรวจ: profile production, ชื่อฐานข้อมูล (ห้าม `_dev` / `_test`), บัญชีสิทธิ์น้อย,
  schema ล่าสุด, ค่า HTTPS ของหน้าเว็บ, โหมด HOSxP และไฟล์ query, ข้อมูลทดลอง MOCK/DEMO, ผู้ดูแลระบบ, master
- ผล **TODO** คือขั้นที่ยังต้องทำ (เช่น ยังไม่มีผู้ดูแลระบบ) ไม่ใช่ข้อผิดพลาด
- ผล **WARN** ของ MOCK/DEMO: ฐานข้อมูลนี้มีข้อมูลทดลองปน ระบบยังเปิดได้ แต่จะแสดงคำเตือนทุกหน้า
  และ**จะไม่ลงบัญชีแผนให้รายการ MOCK** ทางที่ถูกคือใช้ฐานข้อมูลใหม่ที่สะอาด (D-40)

## ขั้นที่ 5 — เปิดระบบครั้งแรก

1. ลงทะเบียน Task Scheduler และเปิดบริการ (`DEPLOY_PRODUCTION.md` §5):
   `tools\ops\register_tasks.ps1 -RunAsUser <บัญชีบริการ> -NightlyTime 01:30 -BackupTime 03:00`
2. ผู้ใช้คนแรก login ผ่านหน้าเว็บ (HTTPS) ด้วยบัญชี HOSxP จริง
   (production ตรวจรหัสผ่านกับ HOSxP เท่านั้น ถ้า HOSxP ล่ม จะ login ไม่ได้ ไม่มีทางเข้าทางอื่น)
3. ให้สิทธิ์ผู้ดูแลระบบคนแรก:
   ```
   .venv\Scripts\python -m ppr.cli grant-role --username <ผู้ใช้> --role ADMIN
   ```
4. ผู้ดูแลระบบ sync master จาก HOSxP กำหนดบทบาทผู้ใช้อื่น และแต่งตั้งหัวหน้าเจ้าหน้าที่พัสดุของปีงบ
5. เจ้าหน้าที่แผนสร้างปีแผน นำเข้าแผนที่อนุมัติ แล้วเปิดใช้ (ACTIVE)
6. รัน `first-start --check` อีกครั้ง บรรทัดผู้ดูแลระบบและ master ควรเป็น PASS
   (บรรทัด backup และ hosxp-verify เป็น TODO เสมอ เพราะคำสั่งนี้ไม่ได้ตรวจเอง หลักฐานอยู่ใน checklist A3, A8)
7. สำรองข้อมูลครั้งแรกและทดลองกู้คืน (`DEPLOY_PRODUCTION.md` §7)
8. ตรวจสถานะ: `tools\ops\status.ps1` → `status: PASS`
   (ถ้ามีบรรทัด WARN ให้อ่าน และบันทึกใน checklist ส่วน B)
